Color Layout Fixtures And Screenshot Testing

Color layout fixtures are small HTML/CSS pages that replace real content with colored blocks. They make layout geometry visible without needing to interpret text or images.

This technique is useful when a real page has too much complexity. A focused fixture can isolate one layout rule: flex auto sizing, grid columns, inline links, image placeholders, percentage widths, or nested blocks.

How This Relates To AlmostThere Browser

AlmostThere uses fixtures to turn live-page symptoms into repeatable tests. If Ecosia, Wikipedia, or a weather page breaks, the goal is not to hardcode that site. The goal is to extract the general HTML/CSS pattern and preserve it in color_layout_test/.

The same fixture can be rendered by the browser and by a reference browser. Paired images make differences visible.

Fixture Design

A good fixture is:

  • small,
  • focused on one behavior,
  • visually obvious,
  • close enough to the real page pattern,
  • not copied wholesale from copyrighted pages,
  • stable across test runs.

Use colored backgrounds, labels where useful, and simple dimensions. Avoid importing remote assets.

Synthetic And Actual Rendering

Synthetic rendering is fast and useful for testing the internal renderer directly. Actual-browser rendering is slower but catches whether changes reach the visible browser path.

Both modes are useful. A fixture passing synthetically but failing in the actual browser suggests the bug is after fixture generation or in the real rendering path.

Reference Comparisons

Reference screenshots from Chrome or Firefox show expected browser behavior. Manual inspection is still important because exact pixel matching can overfocus on fonts or antialiasing while missing the real structural issue.

Paired images should clearly separate "This browser" and "Reference", with an unmistakable divider.

Debugging This Layer

When a fixture fails, inspect:

  • the HTML/CSS pattern,
  • computed style,
  • layout boxes,
  • render graph,
  • paired screenshot,
  • whether the fixture faithfully represents the live page.

If the fixture passes but the live page still fails, add a more faithful fixture rather than weakening the fix.

Rust Shape

Fixture tests should describe the fixture, render mode, and generated artifacts explicitly.

struct LayoutFixture {
    id: u32,
    name: String,
    html_path: PathBuf,
}

enum FixtureRenderMode {
    Synthetic,
    ActualBrowser,
}

struct FixtureResult {
    fixture_id: u32,
    screenshot_path: PathBuf,
    reference_path: Option<PathBuf>,
    paired_path: Option<PathBuf>,
}

fn render_fixture(fixture: &LayoutFixture, mode: FixtureRenderMode) -> Result<FixtureResult, TestError> {
    todo!("render the fixture and write screenshots")
}

Keeping artifact paths in the result makes it easier to inspect failures manually.
