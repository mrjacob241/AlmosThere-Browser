Image Loading And Late Resource Updates

Images are replaced elements: the HTML node reserves a box, but the visible content comes from an external resource. Unlike text, image data may arrive after the first page paint.

AlmostThere uses placeholders for unavailable images and replaces them when loading succeeds. This lets the page become readable before every image is complete.

How This Relates To AlmostThere Browser

The HTML parser discovers image URLs. The loader resolves them. The image scheduler decides when to request them. The decoder turns bytes into dimensions and pixels. The render pipeline shows a placeholder until a decoded image is available, then updates the page.

Late image loading must be tied to the correct page and tab. If a tab closes or navigates away, pending image requests should be canceled, ignored, or drained safely.

Placeholders

A missing image should not show a raw filename as page text. A neutral placeholder rectangle communicates that an image area exists while preserving layout stability.

When debug image loading is enabled, the placeholder can show loading status or failure reason. This should be diagnostic text, not normal page content.

Scheduling

Image scheduling balances speed and politeness. Requesting every image at once can overwhelm small servers or create repeated collisions. Requesting one at a time can be slow but predictable.

A conservative browser can:

  • collect images during page analysis,
  • sort visible or earlier images first,
  • avoid duplicate in-flight requests for the same URL,
  • pace requests with a small delay or gate,
  • retry failures cautiously,
  • record timings in telemetry.

Late Updates

When an image finishes after first paint, the browser needs to update visible state. If the intrinsic size was unknown, layout may need to run again. If the placeholder already reserved the final size, repaint may be enough.

Late updates should be incremental where possible. Loading one image should not require a full navigation restart.

Debugging This Layer

Image telemetry should answer:

  • when the URL was discovered,
  • when it was scheduled,
  • when the request started,
  • whether it reused HTTP/2 or HTTP/1 behavior,
  • whether it succeeded, failed, or retried,
  • what dimensions were decoded,
  • whether a placeholder was updated.

Network graphs are useful for seeing request collisions, pacing, retries, and stalls.

Rust Shape

Images should have explicit lifecycle states so placeholders, retries, and late updates are easy to reason about.

enum ImageState {
    Queued,
    Loading { started_ms: u64 },
    Loaded { width: u32, height: u32, bytes: Vec<u8> },
    Failed { reason: String },
}

struct ImageRequest {
    id: ImageId,
    page_id: PageId,
    node_id: NodeId,
    url: String,
    state: ImageState,
}

fn apply_image_result(page: &mut PageState, result: ImageResult) {
    if page.id == result.page_id {
        page.images.insert(result.image_id, result.state);
    }
}

The page id check prevents old image work from updating a tab after navigation.
