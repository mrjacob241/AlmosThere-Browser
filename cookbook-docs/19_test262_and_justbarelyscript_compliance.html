test262 And JustBarelyScript Compliance

JustBarelyScript is the JavaScript engine used by the browser. It needs enough ECMAScript behavior to run real page scripts and enough test coverage to avoid regressing language semantics.

test262 is the official ECMAScript conformance test suite. AlmostThere may run subsets or derived built-in tests to measure practical progress.

How This Relates To AlmostThere Browser

Browser pages often depend on standard JavaScript behavior indirectly through libraries. A site may not look like it uses typed arrays, promises, descriptors, or strict mode, but its bundled code may rely on them.

Improving JustBarelyScript compliance makes page-specific scripts less fragile. It also reduces the need for ad hoc host API patches.

Built-Ins

Built-ins are standard objects and functions such as:

  • Object,
  • Array,
  • String,
  • Number,
  • Promise,
  • Map,
  • Set,
  • ArrayBuffer,
  • TypedArray,
  • DataView.

Each built-in has detailed semantics. A method may care about this, constructor behavior, property descriptors, iteration order, species constructors, or abrupt completions.

Test Percentages

Percentages are only meaningful if the denominator is clear. A score over a small selected subset is not the same as total ECMAScript compliance.

Always state whether a percentage refers to:

  • all discovered tests,
  • enabled built-in tests,
  • a specific block,
  • passing tests after exclusions,
  • runtime-reachable browser tests.

Standards-Oriented Fixes

JavaScript fixes should follow ECMAScript semantics where possible. If exact compliance is too large for one change, implement the most general correct subset and document the limitation.

Avoid fixing only the call shape seen on one page. For example, an Array.from fix should work through the shared function behavior, not just through one bundled library pattern.

Debugging This Layer

When a built-in test fails, inspect:

  • expected value,
  • actual value,
  • thrown exception,
  • strict mode,
  • this binding,
  • property attributes,
  • iterator behavior,
  • constructor path.

After a fix, rerun the smallest relevant test block first, then broader built-in tests.

Rust Shape

JavaScript compliance work benefits from small test records with clear expected outcomes.

struct BuiltinTest {
    name: String,
    source: String,
    expected: ExpectedOutcome,
}

enum ExpectedOutcome {
    Value(String),
    Throws(String),
    Pass,
}

struct TestSummary {
    total: usize,
    passed: usize,
    failed: usize,
    skipped: usize,
}

fn run_builtin_test(runtime: &mut JsRuntime, test: &BuiltinTest) -> TestResult {
    todo!("execute source and compare with expected outcome")
}

Always report which test set produced a percentage; otherwise the number is easy to misread.
