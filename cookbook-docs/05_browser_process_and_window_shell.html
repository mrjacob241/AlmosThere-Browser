Browser Process And Window Shell

The browser shell is the visible application around the page. It owns the window, toolbar, tabs, menus, loading indicators, status labels, and the connection between user commands and page work.

AlmostThere Browser uses this shell as the stable part of the application. Pages can be slow, malformed, script-heavy, or crash-prone, but the user should still be able to see progress, switch tabs, stop using a broken page, and inspect diagnostics.

How This Relates To AlmostThere Browser

The shell is where browser state becomes interactive. It stores the current tabs, selected tab, navigation controls, preferences, debug flags, and loading progress. It does not need to know every detail of HTML or CSS, but it needs clear messages from page workers: page loaded, resource failed, image updated, script errored, render tree ready, or page apparently crashed.

The important boundary is responsiveness. The GUI thread should spend its time drawing controls and applying completed updates. Expensive work such as network fetches, parsing, JavaScript execution, image loading, and layout should happen in page-oriented workers or in bounded chunks.

Shell Responsibilities

The shell typically handles:

  • URL bar input,
  • back, forward, reload, and debug controls,
  • tab creation and selection,
  • menus for history and preferences,
  • loading labels and progress bars,
  • scroll and zoom input,
  • context menu commands,
  • debug flags and telemetry options,
  • routing completed page output into the visible canvas.

The shell should not become a second layout engine. It should host the browser view and controls, then delegate page content to the page pipeline.

Page Work Boundary

A page worker performs the work that belongs to one page or tab. That includes loading the document, resolving resources, parsing HTML, collecting CSS, running scripts, laying out content, and returning renderable output.

The shell and page worker should communicate through explicit state updates. Good messages are concrete: navigation started, loading progress changed, image completed, layout finished, script failed, or worker crashed. Vague shared state makes race conditions harder to debug.

When a tab is closed, its page work should stop or become ignored. Late resource completion must not update a tab that no longer exists.

Failure Isolation

The shell is the fallback when page work fails. If a script overflows the stack, a resource hangs, or a page worker crashes, the shell should be able to show an error state rather than disappearing with the page.

This is why the process model matters. Browser-like applications separate the stable UI from unreliable page content. AlmostThere does not need the full sophistication of Chrome's process model, but it should preserve the same design principle: broken content should not take down the whole browser interface.

Debugging This Layer

If the UI freezes, first check whether page work is running on the same path as UI updates. If a tab shows stale content, check whether a late page-worker message was applied to the wrong selected tab. If progress labels are misleading, check whether they are tied to real loading state or to timeout counters.

Good shell bugs usually include:

  • the selected tab before and after the action,
  • the page-worker message that arrived,
  • whether the GUI remained repainting,
  • whether the action affected the intended tab,
  • whether telemetry was flushed before failure.

Rust Shape

The shell is usually a stateful object updated once per GUI frame. Page work arrives as messages that mutate tab state.

struct BrowserApp {
    tabs: Vec<TabState>,
    selected_tab: Option<TabId>,
    pending_messages: Vec<PageMessage>,
}

enum PageMessage {
    LoadingProgress { tab_id: TabId, label: String, percent: f32 },
    RenderReady { tab_id: TabId, scene: CanvasScene },
    PageCrashed { tab_id: TabId, reason: String },
}

impl BrowserApp {
    fn apply_message(&mut self, message: PageMessage) {
        match message {
            PageMessage::RenderReady { tab_id, scene } => {
                if let Some(tab) = self.tabs.iter_mut().find(|tab| tab.id == tab_id) {
                    tab.scene = Some(scene);
                }
            }
            PageMessage::LoadingProgress { .. } | PageMessage::PageCrashed { .. } => {
                todo!("update tab status")
            }
        }
    }
}
