Navigation, Tabs, History, And Preferences

Navigation is the path from an address or click to a new page state. Tabs organize multiple page states in one window. History remembers where the user has been. Preferences provide stable defaults such as homepage and new-tab page.

These features look simple in the UI, but they are coordination systems. They decide which page worker starts, which tab receives a result, what URL is stored, and what the browser does when the user presses back, forward, reload, or opens a new tab.

How This Relates To AlmostThere Browser

AlmostThere treats navigation as a browser-level command. The command may come from the URL bar, a bookmark, a history entry, a link hit box, form submission, or JavaScript navigation effect. Once accepted, it creates or updates a tab state and starts page loading.

The tab state should keep the currently visible page separate from other pages. Selecting a tab should switch the canvas to that tab's render output. Opening a new tab should create an independent page worker while using configured defaults for the initial URL.

URL Normalization

Users often enter partial addresses. A browser needs rules for turning text into a loadable URL. Examples include:

  • keeping https://example.org as an HTTPS URL,
  • preserving file:///... local pages,
  • treating search text as a search query when appropriate,
  • resolving relative links against the current page URL.

Normalization should happen before history and loading so all downstream layers agree about the address.

Tabs

A tab usually stores:

  • tab id,
  • current URL,
  • title or display name,
  • loading state,
  • history position,
  • rendered page state,
  • page-worker handle or channel,
  • errors and diagnostics.

The selected tab controls what the user sees. Other tabs may still load resources or finish work in the background, but their updates must be routed by tab id, not by "whatever tab is selected now".

History

History has two meanings. Per-tab history supports back and forward. Browser-wide history records visited addresses with a title and timestamp.

The persisted history format should be simple and durable. A JSON entry can store:

{
  "url": "https://example.org/",
  "title": "Example Domain",
  "timestamp": "2026-06-10T12:00:00Z"
}

Back and forward should move within the tab's own chronology. Browser-wide history should support the menu view and later user workflows without changing the current tab unless the user selects an entry.

Preferences

Preferences are user-editable defaults. For now the important values are homepage and tabpage. These should be loaded from JSON, shown in the preferences UI, saved when the user requests it, and reset from disk when requested.

Preferences should not be hardcoded across the codebase. The shell should ask the preferences layer for the default page when creating a window or new tab.

Debugging This Layer

If navigation opens in the wrong place, inspect the command source and target tab id. If back or forward jumps unexpectedly, inspect per-tab history. If new tabs load the wrong page, inspect preferences loading and fallback defaults.

Useful traces include:

  • navigation requested,
  • normalized URL,
  • tab id,
  • history push or replacement,
  • selected tab after command,
  • final URL after redirects.

Rust Shape

Navigation should become explicit commands. History and preferences should be ordinary serializable state rather than scattered hardcoded strings.

struct Preferences {
    homepage: String,
    tabpage: String,
}

struct HistoryEntry {
    url: String,
    title: String,
    timestamp_ms: i64,
}

enum NavigationCommand {
    OpenInCurrentTab { tab_id: TabId, url: String },
    OpenInNewTab { url: String },
    Back { tab_id: TabId },
    Forward { tab_id: TabId },
    Reload { tab_id: TabId },
}

This lets URL-bar input, link clicks, history menu clicks, and JavaScript navigation share the same path.
