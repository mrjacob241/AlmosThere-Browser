Introduction

AlmostThere Browser is a small experimental browser written in Rust. It combines an egui desktop shell, a custom HTML/CSS/rendering pipeline, a browser-adapted canvas layer, and a lightweight JavaScript runtime named JustBarelyScript.

The project is not trying to become Chrome or Firefox in one jump. Its current purpose is narrower and more useful for development: load real pages, render enough HTML/CSS to inspect them, run enough JavaScript to support common interactions, record detailed telemetry when something breaks, and make every fix as general and page-agnostic as possible.

The Big Picture

At a high level, the browser works like this:

  • The GUI receives a navigation request from the URL bar, a bookmark, a history entry, a link click, or a form submission.
  • A page-loading worker fetches the main document without freezing the GUI.
  • The loader resolves file, HTTP, and HTTPS resources and records progress.
  • HTML is parsed into an internal document representation.
  • CSS is collected from inline styles, style tags, linked stylesheets, and fallback cached resources.
  • The style layer computes the supported subset of CSS.
  • The layout layer turns DOM/style data into positioned boxes.
  • The render layer lowers those boxes into render graph and canvas graph objects.
  • The canvas paints text, rectangles, images, media placeholders, inputs, links, and hit boxes.
  • User input flows back through link hit testing, editable controls, form metadata, text selection, and JavaScript event hooks.
  • Telemetry records the important events so failures can be understood after the session ends.

Each step is intentionally visible. When a page breaks, the preferred workflow is to find which layer lost information or made a wrong decision, then add a focused fixture or test for that class of problem.

Main Components

The browser has three central implementation areas.

almostthere_browser is the application shell. It owns the desktop window, toolbar, tabs, loading state, history, preferences, debug flags, page worker communication, telemetry, and the glue code that moves data through the browser pipeline.

rich_canvas is the rendering and interaction surface. It paints the final objects, handles scrolling and zooming, supports selectable text, receives pointer events, and provides the canvas primitives used by the browser view.

JustBarelyScript is the JavaScript interpreter. It parses and executes a growing subset of ECMAScript plus browser host APIs. It is used to run page scripts, mutate DOM-like state, dispatch timers/events, and support common browser-bundle patterns.

There are also important supporting folders:

  • sample_pages/ contains local HTML pages and diagnostics used during debugging.
  • color_layout_test/ contains embedded HTML/CSS fixtures for layout comparison.
  • target/ contains generated screenshots, paired references, telemetry outputs, and other build artifacts.
  • appdata/docs/ contains engineering notes and roadmaps.
  • appdata/cookbook/ contains this book.

Design Principles

The browser is built around a few recurring rules.

General fixes are preferred. If a page breaks, the first question is not "how do we patch this site?" but "which browser rule or layout invariant did we miss?"

The pipeline should stay inspectable. A rendered page is the result of HTML parsing, CSS cascade, layout, render graph lowering, canvas graph painting, and event mapping. Debugging is faster when each layer can be inspected separately.

The GUI should stay responsive. Page loading and script work can be slow or broken, so the browser isolates page work from the main GUI enough that buttons, tabs, progress labels, and loading indicators can continue to respond.

Telemetry matters. Many bugs only become obvious after reading JSONL traces, screenshots, render dumps, or network timelines. The browser should make those artifacts easy to generate and compare.

Tests should explain the bug. Color layout fixtures, focused Rust tests, and screenshot comparisons are used not just to prevent regressions, but to describe the layout or runtime rule that was missing.

What "Page-Agnostic" Means Here

A page-agnostic fix is a fix that improves a general browser behavior instead of recognizing a specific page or domain.

Good examples:

  • flex auto sizing should consider child preferred sizes,
  • Array.from should use the same implementation for direct and indirect static calls,
  • links should share text flow with surrounding text and use transparent hit boxes,
  • image placeholders should update when late image loading completes,
  • strict JavaScript callbacks should preserve strict this behavior.

Bad examples:

  • if the URL contains ecosia.org, move a button by 20 pixels,
  • if a Wikipedia title appears, force a custom line height,
  • if an image filename matches one page, skip normal loading rules.

The project has sometimes used site-specific diagnostics to understand a bug, but the final fix should normally live in a general parser, CSS, layout, rendering, network, or runtime rule.

How To Read The Codebase

Start from behavior, not from files. For example, if a link is visible but not clickable, trace it through:

  • HTML anchor extraction.
  • CSS display and text style.
  • inline text shaping and line layout.
  • render graph link span creation.
  • canvas graph transparent hit box creation.
  • pointer hit testing.
  • navigation dispatch.

If text is too narrow, trace DOM content into CSS width rules, flex/grid constraints, preferred child size, layout boxes, render graph objects, and final canvas rectangles.

If JavaScript behaves incorrectly, trace parsing, function creation, strictness, host function dispatch, object/property semantics, and emitted browser effects.

This layered approach is slower than guessing, but it produces fixes that survive the next page.

Section 16, Events, Timers, Dynamic Scripts, And Page Effects, explains the dynamic side of page execution. It covers event dispatch, callbacks, timers, deferred work, dynamic script loading, page mutations, and the rules that prevent one script from freezing the rest of the browser.

Section 18, Color Layout Fixtures And Screenshot Testing, explains the fixture system used to isolate layout bugs. It covers color-coded HTML/CSS pages, synthetic and actual-browser rendering modes, paired screenshots, reference comparisons, and the reason focused fixtures are added before layout changes.

Section 19, test262 And JustBarelyScript Compliance, describes the JavaScript conformance work. It explains how built-in tests are grouped, how percentages are computed, which ECMAScript areas are currently important, and how compliance fixes should be implemented without tailoring behavior to one page.

Section 20, Failure Modes, Crash Isolation, And Recovery, explains what happens when page work fails. It covers script crashes, page-worker failures, stack overflows, resource timeouts, tab-level recovery, user-visible error states, and the design goal that the main GUI should survive broken content.

It covers reading telemetry, starting the debug client, inspecting screenshots, building focused fixtures, comparing reference output, tracing layout objects, and reducing a live-page failure into a small test case.

By the end of the cookbook, a reader should understand how a URL becomes pixels, how a click becomes navigation or script execution, and how to debug the path when one layer gets it wrong.

Rust Shape

The whole browser can be understood as typed stages. Each stage receives one representation and returns the next one.

fn load(url: &str) -> Result<LoadedDocument, LoadError> {
    todo!("fetch or read the main document")
}

fn render_page(loaded: LoadedDocument) -> Result<CanvasScene, BrowserError> {
    let document = parse_html(&loaded.html)?;
    let styles = compute_styles(&document)?;
    let layout = build_layout(&document, &styles)?;
    let render_graph = lower_to_render_graph(&layout)?;
    Ok(build_canvas_scene(&render_graph))
}

The real code has more state and more error cases, but this shape is the mental model: keep every boundary explicit enough to inspect.
