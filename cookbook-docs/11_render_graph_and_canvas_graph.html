Render Graph And Canvas Graph

The render graph is the intermediate representation between layout and painting. It describes what should be drawn without immediately drawing it. The canvas graph is the lower-level representation used by the rendering surface for painting and interaction.

Keeping these layers visible makes debugging much easier. A layout box may be correct while the render graph loses a link span, or the render graph may be correct while the canvas graph creates the wrong hit box.

How This Relates To AlmostThere Browser

AlmostThere lowers layout output into renderable objects: text lines, rich text spans, rectangles, images, placeholders, inputs, buttons, debug overlays, and link hit regions. The canvas then paints those objects and handles user interaction.

This split lets the browser ask precise questions. Did layout produce the right rectangle? Did render graph preserve it? Did canvas graph paint it? Did hit testing attach the expected URL?

Render Objects

Common render objects include:

  • background rectangles,
  • borders and separators,
  • rich text lines,
  • image draws,
  • gray image placeholders,
  • form controls,
  • transparent link hit boxes,
  • selection highlights,
  • debug overlays.

Each object should carry enough geometry and metadata to diagnose later problems. A link span should know its target. An image placeholder should know its resource id or URL. A text line should preserve copy behavior metadata.

Rich Text

Rich text allows one visual line to contain spans with different colors, weights, styles, or underline states. This is important for links inside paragraphs, code snippets with colored spans, and inline emphasis.

The text should be shaped as one flow where possible. Splitting every anchor into a separate text box can create spacing bugs, clipped links, and selection problems.

Canvas Graph

The canvas graph is closer to the drawing backend. It turns render objects into paint calls and interactive regions. It must apply viewport scrolling, zoom scaling, clipping, and selection state consistently.

The canvas graph also owns hit-test behavior. Transparent link boxes may not be visible, but they must line up with the painted text. Debug flags can tint these boxes to make alignment problems visible.

Debugging This Layer

If a box is present in layout but invisible on screen, inspect render graph lowering. If it appears but cannot be clicked, inspect canvas graph hit boxes. If debug link boxes do not match text, fix the mapping between rich text spans and hit regions.

Useful dumps include:

  • layout box rectangle,
  • render object rectangle,
  • canvas object rectangle,
  • text span content,
  • link target,
  • clipping rectangle,
  • zoom and scroll offsets.

Rust Shape

The render graph should preserve visible geometry and interaction metadata before the canvas paints it.

enum RenderObject {
    Rect { rect: Rect, color: Color },
    TextLine { rect: Rect, spans: Vec<TextSpan> },
    Image { rect: Rect, image_id: ImageId },
    Placeholder { rect: Rect, label: Option<String> },
    LinkHitBox { rect: Rect, href: String },
}

struct TextSpan {
    text: String,
    color: Color,
    underline: bool,
    href: Option<String>,
}

Text and link hit boxes can then be compared directly when debugging hover or click alignment.
