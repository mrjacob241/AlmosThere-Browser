Telemetry, Debug Socket, And JSONL Traces

Telemetry is the browser's memory of what happened. It records loading, parsing, script execution, layout, rendering, image scheduling, and user interactions so failures can be inspected after a session ends.

JSONL traces are especially useful because each line is an independent event. A broken session can still leave readable data before a crash or termination.

How This Relates To AlmostThere Browser

AlmostThere relies on telemetry as part of the development workflow. Many bugs are not obvious from the screenshot alone. A page may be blank because the network failed, scripts crashed, layout collapsed, render graph objects were clipped, or the canvas never received an update.

Telemetry provides the timeline needed to identify which layer first diverged.

Debug Socket

The debug socket lets an external client observe or control a running browser session. It is useful for automated runs, repeated page loads, screenshots, and event capture.

The socket should expose useful state without making normal browsing depend on the debug client. If the client disconnects, the browser should continue or fail gracefully.

JSONL Events

A JSONL event should be small, timestamped, and specific. Good event names describe what happened:

  • navigation_started,
  • main_document_loaded,
  • stylesheet_failed,
  • script_budget_exceeded,
  • image_request_started,
  • image_request_finished,
  • layout_completed,
  • render_graph_built,
  • link_hit_tested.

Events should include ids when possible: tab id, page id, resource id, URL, or node id.

Screenshots And Dumps

Telemetry pairs well with screenshots, render dumps, and network graphs. A screenshot shows the symptom. JSONL shows the sequence. A render dump shows geometry. A network graph shows resource timing.

Together they make it possible to debug without guessing.

Debugging This Layer

If telemetry is too vague, add a more precise event at the boundary where information is lost. Avoid logging huge blobs by default. Prefer compact events that can be correlated by id and timestamp.

When adding telemetry, ask which future question it answers. If it does not help diagnose a likely failure, it may become noise.

Rust Shape

Telemetry events should be typed in code and serialized at the boundary.

enum TelemetryEvent {
    NavigationStarted { tab_id: TabId, url: String },
    ResourceLoaded { page_id: PageId, url: String, status: u16, elapsed_ms: u64 },
    ScriptError { page_id: PageId, message: String },
    LayoutCompleted { page_id: PageId, box_count: usize },
}

fn record_event(writer: &mut dyn std::io::Write, event: &TelemetryEvent) {
    let line = format!("{event:?}\n");
    let _ = writer.write_all(line.as_bytes());
}

The production serializer can use JSONL; the important design point is that events are structured before they become text.
