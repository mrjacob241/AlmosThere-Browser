Contribution Checklist

This checklist describes what to verify before considering a browser change complete. It is meant for human contributors and AI coding sessions.

The goal is not bureaucracy. The goal is to prevent fixes that solve the visible symptom while breaking another part of the pipeline.

Before Editing

Understand the layer involved:

  • loading,
  • parsing,
  • CSS,
  • layout,
  • rendering,
  • input,
  • JavaScript,
  • telemetry,
  • tests,
  • shell behavior.

Read nearby code and existing docs before adding a new abstraction.

During Editing

Keep changes scoped. Preserve existing user work. Avoid unrelated refactors. Prefer existing project patterns.

For behavioral fixes, add or update a focused fixture or test where practical. For observability fixes, make telemetry specific and compact.

After Editing

Verify the smallest relevant case first. Then verify broader behavior.

Useful checks:

  • run targeted unit tests,
  • run fixture generation for affected layout cases,
  • inspect paired screenshots,
  • rerun the live page if the bug came from one,
  • inspect latest JSONL telemetry,
  • run built-in JavaScript tests for runtime changes,
  • confirm docs reflect the new behavior.

Documentation

Update documentation when a change affects:

  • browser architecture,
  • debugging workflow,
  • known limitations,
  • test procedures,
  • telemetry format,
  • user-visible behavior,
  • JavaScript support status.

Docs should explain the general rule, not just the page that revealed it.

Commit Readiness

A commit is ready when:

  • the fix is page-agnostic or explicitly justified,
  • relevant tests or fixtures were run,
  • generated artifacts are either intentionally tracked or ignored,
  • docs are updated if needed,
  • the commit message explains the problem and the solution,
  • no unrelated user changes were reverted.

If something could not be tested, state that clearly in the final note or commit message.

Rust Shape

A change can be described as the layers it touched and the checks that were run.

struct ChangeChecklist {
    touched_loading: bool,
    touched_layout: bool,
    touched_javascript: bool,
    fixtures_added: Vec<String>,
    tests_run: Vec<String>,
    docs_updated: bool,
}

impl ChangeChecklist {
    fn ready_for_commit(&self) -> bool {
        self.docs_updated && (!self.tests_run.is_empty() || !self.fixtures_added.is_empty())
    }
}

This is not meant to become a literal gate. It captures the habit: know what changed, prove the relevant behavior, and document the result.
