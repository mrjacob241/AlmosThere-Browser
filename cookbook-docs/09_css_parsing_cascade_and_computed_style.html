CSS Parsing, Cascade, And Computed Style

CSS is the language that tells the browser how HTML should look and how boxes should behave. HTML says "this is a paragraph" or "this is a link"; CSS says whether that paragraph is block-level, how wide it is, what font it uses, what color it has, and how it participates in flex, grid, or normal document flow.

AlmostThere Browser supports a practical subset of CSS. The goal is not to implement the entire platform at once, but to keep the supported subset coherent, child-aware, and close to browser behavior.

How This Relates To AlmostThere Browser

In this browser, CSS is the bridge between parsed structure and physical layout. HTML tells the browser that a node exists; computed CSS tells layout what kind of box that node should create, which text style it should use, how it should size itself, and how it should interact with siblings and children. The layout engine should receive clear computed style data instead of guessing from raw attributes or page-specific patterns.

Most visible page failures pass through this layer. If a selector does not match, the page may lose its intended display mode. If inherited text style is wrong, links, headings, or table cells may look incorrect. If auto, flex, grid, min-width, or percentage behavior is oversimplified, containers can collapse, columns can become too thin, or content can shift across the page. AlmostThere uses focused color layout fixtures because they make this CSS-to-layout contract visible.

Rules And Declarations

A CSS rule has a selector and declarations:

.result-title {
  display: block;
  color: #1a0dab;
  margin-bottom: 4px;
}

The selector .result-title chooses matching elements. Each declaration assigns a property value. Here, the matching element should be displayed as a block, painted blue, and given bottom margin.

Inline styles are declarations written directly on an element:

<div style="display: flex; gap: 12px">

Linked stylesheets come from external files:

<link rel="stylesheet" href="/assets/site.css">

The browser must collect all of these sources before it can compute final style.

The Cascade

The cascade is the rule system that decides which CSS declaration wins when more than one declaration applies.

For example:

a { color: blue; }
.warning a { color: red; }

A link inside an element with class warning should be red because the more specific selector wins. Inline styles usually outrank stylesheet rules. Later rules can override earlier rules when specificity is equal. Some properties inherit from parents, while others do not.

Even a partial browser needs a disciplined cascade. If declarations are applied in arbitrary order, pages may look correct only by accident.

Computed Style

Computed style is the resolved style object that layout consumes. It answers questions like:

  • Is this node display: block, inline, flex, grid, or none?
  • What are its margins, padding, and borders?
  • What font size, weight, color, and line height should text use?
  • Is width auto, fixed, percentage-based, or constrained by min/max rules?
  • Does the element create a replaced box, such as an image?

The important point is that layout should not repeatedly reinterpret raw CSS strings. It should receive normalized values where possible, while preserving enough information to resolve context-dependent values such as percentages and auto.

Display Types

The display property decides what kind of layout behavior an element uses.

block elements normally stack vertically and occupy available inline space. Paragraphs, headings, and many containers behave this way by default.

inline elements participate in text flow. Links, spans, and emphasized text should usually sit inside the same line box as surrounding text.

flex elements lay out their children along a main axis. Flex sizing is child-aware: auto sizes, min-content sizes, and available container space all influence where children go.

grid is also child-aware, but uses rows and columns. Even when the implementation only supports part of grid behavior, it should not collapse tracks to zero when children have real content.

none means the element should not create a visible box and should usually not participate in layout.

Auto Sizing

auto does not mean "zero". In CSS, many automatic sizes are inferred from context and from children.

A block with width: auto inside a normal container usually fills available width. A flex item with automatic size may use its content size, min-content size, flex basis, available space, and min/max constraints. An image without explicit width may use its intrinsic image dimensions. A text container may need enough width to avoid collapsing every word into a vertical column.

This is one of the most important rules in AlmostThere layout work: automatic sizes must be children-aware. If an auto dimension is guessed too early, later layout can collapse, shift right, overflow, or produce columns that are too narrow.

Inheritance And Defaults

Some CSS properties inherit. Text color, font family, font size, and line-height commonly flow from parent to child unless overridden. Box properties such as margin, padding, width, and border usually do not inherit.

Browsers also have default styles. A link is typically blue and underlined on hover, headings are bold and larger, paragraphs have block spacing, and lists have markers. These defaults matter when a page has little CSS or when a stylesheet fails to load.

The default stylesheet should be boring and predictable. It should provide browser-like behavior without hiding bugs from the real cascade.

Debugging This Layer

When layout looks wrong, inspect computed style before blaming the layout algorithm.

Useful checks:

  • Did the expected selector match?
  • Did the winning declaration have the right specificity and order?
  • Did inline style override the stylesheet?
  • Was display parsed correctly?
  • Did inherited text properties reach child nodes?
  • Did auto, percentage, min, and max values survive into layout?

Color layout fixtures are especially useful for CSS bugs. If every box has a visible background color, it becomes obvious whether a size, margin, padding, flex row, or grid track disappeared before painting.

Rust Shape

CSS should be normalized into computed values before layout. Raw strings are useful at parse time, but layout wants typed properties.

enum Display {
    None,
    Block,
    Inline,
    Flex,
    Grid,
}

enum Length {
    Auto,
    Px(f32),
    Percent(f32),
}

struct ComputedStyle {
    display: Display,
    width: Length,
    min_width: Length,
    color: Color,
    font_size_px: f32,
}

This makes unsupported or unknown values explicit and keeps the layout layer from reparsing CSS text.
