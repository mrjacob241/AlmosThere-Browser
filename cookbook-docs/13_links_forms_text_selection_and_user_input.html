Links, Forms, Text Selection, And User Input

User input turns a rendered page back into browser actions. A click can navigate, a form can submit, a drag can select text, a key can edit a field, and a context menu can copy selected content.

This layer is where visual correctness and behavior meet. A link that looks right but cannot be clicked is still broken. Text that can be selected but copies with fake line breaks is only partially working.

How This Relates To AlmostThere Browser

AlmostThere maps canvas events back to page objects. Link text is painted as part of rich text flow, while transparent hit boxes provide clickable regions. Text selection uses rendered text geometry to reconstruct the selected string. Forms use parsed metadata and current input state to build navigation requests.

The goal is browser-like behavior without special casing pages. If a site uses normal anchors, inputs, buttons, or forms, the same implementation should handle it.

Links

An anchor has two parts:

  • visible inline content,
  • navigation metadata such as href.

The visible content should flow like normal text. The clickable region should follow the rendered span. Hover should update cursor and underline behavior where supported. Clicking should resolve the URL against the current page and send a navigation command.

Forms

Forms collect user input and submit it to a target URL. A basic GET form turns field names and values into query parameters. A POST form sends data in the request body.

AlmostThere can start with common GET behavior, but the structure should preserve method, action, input names, button intent, and current values so more complete form support can be added later.

Text Selection

Selection begins at a character boundary and ends at another boundary. It should include the first and last intended characters. It should not add newlines just because a paragraph visually wrapped. Newlines should come from semantic breaks such as block boundaries, explicit line breaks, or preformatted text.

Copy behavior should reconstruct user-visible text in a browser-like way:

  • inline text stays inline,
  • block boundaries may become newlines,
  • visual wraps alone do not create newlines,
  • hidden text is not copied,
  • selected link text copies as text, not as URLs unless a separate command asks for that.

Context Menus

Right clicking selected text should expose text operations such as Copy Text. Context menus should depend on current state: selected text, hovered link, input focus, or empty page area.

The menu should dispatch commands to the browser model instead of directly modifying hidden state inside the canvas.

Debugging This Layer

For links, compare painted text rectangles with transparent hit boxes. For selection, inspect character positions and copied output. For forms, log the action URL, method, field list, and final navigation URL.

Small local pages are enough to test most input behavior. A page with one paragraph, one inline link, one input, and one form can catch many regressions.

Rust Shape

Input handling should convert low-level pointer and keyboard events into page actions.

enum InputAction {
    Navigate(String),
    StartSelection { point: Point },
    ExtendSelection { point: Point },
    SubmitForm { form_id: NodeId },
    FocusInput { node_id: NodeId },
    CopySelectedText,
}

fn handle_click(hit: HitTarget) -> Option<InputAction> {
    match hit {
        HitTarget::Link { href } => Some(InputAction::Navigate(href)),
        HitTarget::Input { node_id } => Some(InputAction::FocusInput { node_id }),
        HitTarget::Text { .. } => None,
    }
}

This keeps link navigation, form work, and text selection from being hidden inside drawing code.
