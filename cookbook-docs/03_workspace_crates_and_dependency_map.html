Workspace Crates And Dependency Map

AlmostThere is a Cargo workspace. A workspace lets several related Rust crates share one dependency lockfile, edition, version, and build command.

The root Cargo.toml currently defines three first-party crates:

[workspace]
members = ["almostthere_browser", "rich_canvas", "JustBarelyScript"]
default-members = ["almostthere_browser"]
resolver = "2"

First-Party Crates

almostthere_browser is the application crate. It owns the GUI shell, tabs, navigation, loading, preferences, telemetry, browser pipeline integration, and executable entry point.

rich_canvas is the rendering surface crate. It provides canvas-oriented drawing and interaction primitives used by the browser view.

justbarelyscript is the JavaScript runtime crate. It implements the ECMAScript subset, built-ins, execution model, and browser-facing host integration points.

Dependency Direction

The dependency direction should stay simple:

almostthere_browser
  -> rich_canvas
  -> justbarelyscript

In practice, almostthere_browser depends on both rich_canvas and justbarelyscript. The canvas crate should not depend on the browser shell, and the JavaScript runtime should remain usable as a runtime crate instead of knowing about one page's layout code.

Important External Crates

The root workspace dependencies include:

eframe = "0.33"
egui = "0.33"
image = { version = "0.25", features = ["avif-native"] }
libc = "0.2"
reqwest = { version = "0.12", default-features = false, features = ["blocking", "rustls-tls", "http2"] }
winit = "0.30"

eframe and egui provide the desktop GUI surface. winit supports window/event integration. reqwest performs HTTP and HTTPS requests with Rustls TLS and HTTP/2 support. image decodes image assets. libc is available to the JavaScript runtime for low-level integration needs.

HTTP Library And Browser Architecture

AlmostThere uses reqwest as its HTTP client library:

reqwest = { version = "0.12", default-features = false, features = ["blocking", "rustls-tls", "http2"] }

The selected features are part of the architecture:

  • blocking means page workers can perform straightforward synchronous request code without making the GUI event loop async-aware.
  • rustls-tls provides HTTPS without depending on platform-native TLS bindings.
  • http2 allows the loader to negotiate HTTP/2 when the server supports it, while still keeping HTTP/1 behavior as the fallback.
  • default-features = false keeps the dependency surface explicit instead of silently enabling unrelated networking features.

reqwest should stay inside the browser loading layer. The GUI should not issue HTTP requests directly. The canvas should not know that HTTP exists. The JavaScript runtime should request network-like effects through browser host APIs rather than importing reqwest itself.

The intended dependency relationship looks like this:

egui shell
  -> browser loading service
      -> reqwest HTTP client
      -> file loader
  -> HTML/CSS/JS/page pipeline
  -> rich_canvas

This separation keeps networking replaceable. If the project later adds a more advanced HTTP/2 scheduler, cache layer, service worker model, or async loader, the rest of the browser should still receive the same typed resource responses.

struct HttpClientConfig {
    user_agent: String,
    accept_language: String,
    timeout_ms: u64,
    enable_http2: bool,
}

struct BrowserHttpClient {
    config: HttpClientConfig,
}

impl BrowserHttpClient {
    fn fetch(&self, request: ResourceRequest) -> Result<ResourceResponse, LoadError> {
        todo!("wrap reqwest and return browser-owned response data")
    }
}

The wrapper is important. Most browser code should work with ResourceRequest, ResourceResponse, and LoadError, not with raw reqwest types.

The application crate also uses tiny-skia for raster-oriented drawing support:

tiny-skia = { version = "0.11.4", default-features = false, features = ["std", "simd"] }

justbarelyscript currently uses rayon for parallel test or runtime support where appropriate:

rayon = "1"

How This Relates To AlmostThere Browser

Crate boundaries should reflect architectural boundaries. The browser shell can coordinate everything, but rendering primitives belong in rich_canvas, and JavaScript semantics belong in justbarelyscript.

When a feature crosses crates, prefer a small typed API between crates. For example, JavaScript can emit browser effects, and the browser can apply those effects to page state. The JS crate should not directly paint pixels, and the canvas crate should not fetch web pages.

Cargo Commands

Common workspace commands:

cargo build
cargo test
cargo run -p almostthere_browser
cargo run -p almostthere_browser -- --debug-socket --record-events --event-trace

Use package-specific commands when you only need one crate. Use workspace commands when checking integration.
