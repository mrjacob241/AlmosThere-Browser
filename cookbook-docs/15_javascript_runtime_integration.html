JavaScript Runtime Integration

JavaScript is the language that makes many pages dynamic. HTML creates the initial structure, CSS describes presentation, and JavaScript can inspect the page, respond to events, fetch or reveal content, update styles, and schedule work for later.

AlmostThere Browser uses a lightweight JavaScript runtime named JustBarelyScript. The aim is practical browser compatibility: implement enough ECMAScript and browser host behavior to support common pages, while keeping script failures isolated and visible.

How This Relates To AlmostThere Browser

In this browser, JavaScript is not an isolated interpreter bolted onto the side. It is connected to the loaded page through host APIs, events, timers, DOM-like state, style mutation, navigation effects, and telemetry. A script can change what the user sees by adding text, changing display, updating classes, submitting forms, or scheduling later work. The runtime therefore feeds back into parsing-derived state, computed style, layout invalidation, rendering, and user interaction.

The important implementation rule is that scripts should produce browser effects, not directly paint the page. JustBarelyScript evaluates code and calls host APIs; the browser applies the resulting mutations through the same general document, style, layout, and render pipeline used for static HTML. This keeps fixes page-agnostic: implementing a standard array behavior, timer rule, DOM mutation, or style update helps every page that relies on that behavior.

ECMAScript And Browser APIs

JavaScript the language is standardized as ECMAScript. It defines values, objects, functions, arrays, promises, typed arrays, classes, strict mode, property descriptors, and the built-in objects such as Array, String, Object, Map, and Promise.

Browser APIs are a separate layer. They include objects such as window, document, elements, timers, events, storage, location, and network APIs. A script running in a browser normally uses both layers at once:

document.querySelector(".temperature").style.display = "block";
setTimeout(() => console.log(location.href), 1000);

The first line needs DOM querying and style mutation. The second line needs timers, callbacks, console output, and location state.

Why Scripts Matter For Rendering

Some pages are mostly static HTML. Others hide important content until a script runs.

A weather page may ship a table where temperature cells start hidden, then call a helper such as .show() or set style.display after data is prepared. A search page may attach form handlers after loading. A menu may become usable only after a click listener is installed.

If JavaScript fails, the page can look like a layout bug even when HTML and CSS are correct. That is why script telemetry is important: the browser should record which scripts loaded, which ones ran, which host APIs were called, and which errors stopped execution.

Host Objects

Host objects are the browser-provided objects exposed to JavaScript. They are not part of the pure ECMAScript language, but web scripts expect them to exist.

Common examples:

  • window for global browser state,
  • document for page structure,
  • location for the current URL,
  • console for logs and warnings,
  • setTimeout and clearTimeout for timers,
  • element objects for attributes, style, classes, and events.

The host layer should be general. If a page calls element.style.display = "none", the implementation should update element style in a normal way, not check which website made the call.

Effects And Mutations

The JavaScript runtime should not paint directly. Instead, it should produce browser effects that the page model can apply.

Examples of effects:

  • set an attribute,
  • change inline style,
  • add or remove a class,
  • update text content,
  • reveal or hide an element,
  • submit a form,
  • schedule a timer,
  • trigger navigation,
  • report a console message.

This separation makes debugging easier. If a script called .show() and the element stayed hidden, the bug might be in the host method, the effect application, style recomputation, layout invalidation, or painting. Telemetry should make that chain inspectable.

Events And Callbacks

Pages react to events. A click, key press, input change, timer tick, or load completion can call JavaScript code.

The browser needs to preserve enough event information for handlers to behave naturally:

  • the event type,
  • the target element,
  • basic pointer or keyboard data,
  • whether default behavior was prevented,
  • which callback should be invoked.

Callbacks must also preserve JavaScript semantics. Strict mode, this binding, argument order, return values, and thrown errors all matter. Small deviations can make generic libraries fail in surprising ways.

Budgets And Failures

Real browsers do not let one broken script permanently freeze the whole browser UI. AlmostThere should follow that principle.

Script execution needs budgets, recursion guards, and clear failure reporting. If a script runs too long, recurses too deeply, or throws an unsupported-operation error, the browser should record a specific diagnostic event and keep the tab or page shell recoverable where possible.

A script failure is not always fatal to rendering. The static page may still be useful. The key is to fail visibly in telemetry and conservatively in the UI, rather than silently corrupting later stages.

Compliance Work

JustBarelyScript is measured partly with built-in tests and test262-derived work. These tests help separate real language conformance from page-specific compatibility.

When a built-in fails, the fix should usually live in the shared runtime implementation. For example, Array.from, typed arrays, promises, strict callbacks, and property behavior should be implemented according to the standard so many scripts benefit at once.

The same rule applies to browser APIs. Implement .show(), .hide(), .css(), .each(), or DOM methods because they express common web behavior, not because a single page happens to call them.

Debugging This Layer

When a page is structurally present but interactive content is missing, inspect JavaScript before changing CSS or layout.

Useful questions:

  • Did the script resource load?
  • Did it execute or time out?
  • Which exception or unsupported operation occurred?
  • Did a host API call produce the expected browser effect?
  • Was style recomputed after a mutation?
  • Did a timer or event handler run?
  • Did telemetry show a script-specific error in the browser console?

A good JavaScript fix should improve a standard behavior, pass or unlock relevant built-in tests, and leave enough telemetry to diagnose the next unsupported script pattern.

Rust Shape

The JavaScript runtime should emit effects that the browser applies through normal page systems.

enum JsValue {
    Undefined,
    Bool(bool),
    Number(f64),
    String(String),
    Object(ObjectId),
}

enum BrowserEffect {
    SetStyle { node_id: NodeId, property: String, value: String },
    SetText { node_id: NodeId, text: String },
    AddEventListener { node_id: NodeId, event: String, callback: ObjectId },
    ConsoleMessage { level: String, text: String },
}

fn run_script(source: &str, host: &mut HostContext) -> Result<Vec<BrowserEffect>, JsError> {
    todo!("parse and execute JavaScript with browser host APIs")
}

The runtime should not directly paint or lay out content; it asks the browser to mutate page state.
