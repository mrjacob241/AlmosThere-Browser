HTML Parsing And DOM Extraction

HTML is the language that describes the content structure of a web page. It is not a pixel format. It tells the browser that some text is a heading, some content is a paragraph, some element is a link, and some resource should be loaded, but CSS and layout decide where most things actually appear.

AlmostThere Browser parses HTML into an internal document representation. That representation is then used by style computation, layout, rendering, JavaScript host APIs, link hit testing, forms, text selection, and telemetry.

How This Relates To AlmostThere Browser

In this browser, HTML parsing is the point where network bytes become page structure. The loader may have fetched a valid document, but the rest of the browser cannot use it until the parser has identified elements, text, attributes, resource references, controls, links, scripts, and style blocks. The parser is therefore the input contract for CSS, layout, rendering, interaction, JavaScript, and debug output.

When the parser makes a mistake, the symptom often appears somewhere else. A dropped space around an inline tag becomes awkward text spacing. A lost href becomes a visible link that cannot navigate. A malformed tree becomes a flex or block layout that shifts to the wrong side of the page. A missed <script> means JavaScript never gets a chance to reveal dynamic content. AlmostThere's parser should therefore preserve source meaning carefully, even when the renderer only supports part of the full web platform.

HTML Is A Tree

Most HTML can be understood as a tree of elements and text nodes.

<article>
  <h1>Hello world</h1>
  <p>Read the <a href="/wiki/C">C article</a>.</p>
</article>

This becomes a structure like:

article
  h1
    text: "Hello world"
  p
    text: "Read the "
    a href="/wiki/C"
      text: "C article"
    text: "."

The distinction between elements and text is important. The <a> element creates link behavior, but the visible words still need to participate in normal inline text flow with the surrounding text.

Tags, Attributes, And Text

An opening tag starts an element:

<a href="/search?q=hello">hello</a>

The tag name is a. The attribute name is href. The attribute value is /search?q=hello. The text content is hello.

The parser must preserve enough of this information for later stages. If the parser drops a space around a tag, the page may render words too close together. If it loses an href, the text may still be visible but no longer clickable. If it misreads an image src, the browser may show a placeholder forever.

HTML Is Forgiving

Real HTML is often imperfect. Browsers are expected to recover from missing closing tags, optional tags, unexpected nesting, comments, entities, and mixed casing.

For example:

<p>First paragraph
<p>Second paragraph

A browser should treat this as two paragraphs even though the first </p> is missing. A small experimental parser does not need to implement every edge case at once, but it should prefer browser-like recovery over crashing or discarding large parts of the page.

Whitespace Matters

HTML text whitespace is subtle. In normal flow, multiple spaces often collapse visually to one space, and newlines in the source usually behave like spaces. In preformatted contexts such as <pre>, whitespace should be preserved more literally.

This matters especially around inline tags:

The <a href="/wiki/C">C language</a> is standardized.

The visible result should contain natural spacing around the link. The parser should not delete the space before or after the anchor just because an element boundary exists there. Later text layout should handle wrapping and spacing as a single inline flow, not as disconnected text boxes that accidentally create gaps or overlaps.

Important Elements

Some HTML elements carry special meaning for a browser:

  • <a> creates navigation targets,
  • <form> groups controls and submission metadata,
  • <input> and <textarea> create editable controls,
  • <button> creates clickable actions,
  • <img> creates replaced content and a resource request,
  • <script> adds executable JavaScript,
  • <style> adds embedded CSS,
  • <link> can add external stylesheets, icons, or metadata,
  • <pre> changes whitespace handling,
  • headings and paragraphs influence default display and spacing.

The parser should extract these meanings without making page-specific assumptions. A malformed or unsupported element should normally degrade into ordinary content rather than breaking the whole tree.

DOM Extraction

The DOM in a full browser is a live object model that JavaScript can inspect and mutate. AlmostThere does not need a complete browser DOM to render pages, but it still needs a DOM-like internal structure.

The extraction layer should answer questions such as:

  • What text exists, and in what order?
  • Which attributes belong to which element?
  • Which URLs should be resolved and loaded?
  • Which nodes are links or controls?
  • Which scripts and styles should be collected?
  • Which nodes should be exposed to JavaScript host APIs?

That document model is the bridge between parsing and every later browser layer.

Debugging This Layer

When text is missing, links do not click, forms submit the wrong URL, or image placeholders show filenames instead of loading assets, inspect HTML extraction before changing layout.

A good parser bug report should identify:

  • the original source snippet,
  • the internal node or attribute that was produced,
  • the expected browser-like interpretation,
  • the later symptom caused by the mismatch.

Focused fixture pages are useful here. A ten-line HTML file can prove whether the parser preserves spaces, attributes, nesting, and resource URLs before a full live page adds unrelated complexity.

Rust Shape

HTML parsing should preserve element identity, attributes, text, and source order.

type NodeId = u64;

enum NodeKind {
    Element(ElementData),
    Text(String),
    Comment(String),
}

struct ElementData {
    tag_name: String,
    attributes: Vec<(String, String)>,
    children: Vec<NodeId>,
}

struct Document {
    nodes: Vec<NodeKind>,
    root: NodeId,
}

Later layers can then ask clear questions: which node is an anchor, which node is text, and which node references a resource.
