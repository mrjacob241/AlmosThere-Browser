Loading Pages And Resources

Loading is the part of the browser that turns an address into bytes. It is where a URL such as https://www.example.org/page.html becomes an HTML document, where linked stylesheets and scripts are discovered, and where image resources are scheduled for later decoding and display.

In AlmostThere Browser this layer has two jobs. First, it must behave enough like a normal browser that real pages can load. Second, it must stay observable, because loading bugs often look like layout bugs until telemetry shows that a stylesheet, script, image, redirect, or response header never arrived.

How This Relates To AlmostThere Browser

In this browser, loading is the first half of navigation. The GUI asks for a URL, but the page worker does the expensive work: resolve the address, fetch the document, collect dependent resources, and report progress back to the tab. The output of this layer is not pixels; it is a loaded document plus resource data that can be handed to HTML parsing, CSS collection, JavaScript execution, image scheduling, history updates, and telemetry.

This means a loading bug can damage every later stage. If the main response is wrong, the parser receives the wrong HTML. If a stylesheet is missing, layout may look broken even though the layout code did what it was told. If an image request is delayed or fails, the renderer should show a placeholder and later replace it when the image arrives. If a script resource fails, dynamic content may never appear. For that reason, AlmostThere treats the loader as both a data pipeline and a diagnostic boundary.

What A URL Means

A URL is not just a string for the address bar. It is a structured identifier with a scheme, host, path, query, and sometimes a fragment.

For example:

https://www.ecosia.org/search?method=index&q=hello+world

The scheme is https, the host is www.ecosia.org, the path is /search, and the query is method=index&q=hello+world. The browser uses those parts to decide which loader to use, how to resolve relative links, and what should be shown in history or telemetry.

Local files use a different scheme:

file:///home/user/sample_pages/page.html

For a file: URL, the browser reads from disk. For http: and https:, it opens a network connection. For relative links such as ../style.css, the browser resolves the link against the current document URL before fetching it.

HTTP In Plain Terms

HTTP is a request-response protocol. The browser sends a request that says, roughly, "give me this resource", and the server sends back a response containing a status code, headers, and an optional body.

A simplified request looks like this:

GET /wiki/Hello_world HTTP/1.1
Host: it.wikipedia.org
User-Agent: AlmostThere
Accept: text/html
Accept-Language: it-IT,it;q=0.9,en-US;q=0.8,en;q=0.7

A simplified response looks like this:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 12345

<!doctype html>
<html>...</html>

The status code says what happened. 200 means success, 301 and 302 usually mean redirect, 404 means not found, and 500 means the server failed. Headers describe the response. The body contains the actual HTML, CSS, JavaScript, image bytes, or other resource data.

HTTP/1 And HTTP/2

HTTP/1 usually treats each request as a mostly independent exchange, even when connections are reused. This is simple but can be slow when a page has many small assets.

HTTP/2 lets multiple requests share one connection more efficiently. It can reduce connection overhead and allows multiplexing, where more than one response can be in flight at the same time. In a browser, HTTP/2 is useful for pages with many images, scripts, and stylesheets, but it must still be managed carefully so the browser does not flood a server or lose track of resource completion.

AlmostThere keeps HTTP/1 behavior as the fallback path. HTTP/2 support should improve loading when available, but a failed HTTP/2 attempt must not make a page unloadable if HTTP/1 would work.

HTTP Library Used By The Browser

AlmostThere uses the Rust crate reqwest for HTTP and HTTPS transport. In the workspace it is configured like this:

reqwest = { version = "0.12", default-features = false, features = ["blocking", "rustls-tls", "http2"] }

This choice means the browser does not implement TCP, TLS, redirects, header parsing, or HTTP/2 framing directly. Those transport concerns are delegated to reqwest. The browser still owns browser-level policy: which URL to request, which headers to send, how long to wait, how to classify the resource, how to schedule image requests, how to record telemetry, and what to do with the response body.

The feature choices are deliberate:

  • blocking fits the current page-worker model. The GUI remains responsive because blocking requests happen away from the GUI frame loop.
  • rustls-tls handles HTTPS in a cross-platform Rust TLS stack.
  • http2 lets reqwest negotiate HTTP/2 for servers that support it.
  • default-features = false keeps the enabled networking behavior visible in Cargo.toml.

The architecture should wrap reqwest behind browser-owned types:

struct BrowserLoader {
    http: BrowserHttpClient,
    file_loader: FileLoader,
    telemetry: TelemetrySink,
}

impl BrowserLoader {
    fn load(&self, request: ResourceRequest) -> Result<ResourceResponse, LoadError> {
        match request.scheme() {
            "file" => self.file_loader.load(request),
            "http" | "https" => self.http.fetch(request),
            scheme => Err(LoadError::UnsupportedScheme(scheme.to_string())),
        }
    }
}

That wrapper is the contract between the HTTP library and the browser. reqwest returns network responses; the browser converts them into page-pipeline data. After conversion, HTML parsing, CSS collection, JavaScript loading, image decoding, and telemetry should not need to depend on reqwest details.

Request And Response Mapping

A browser request contains more information than a URL. It includes the resource kind, page id, tab id or page id for stale-update protection, headers, timeout policy, and debug metadata.

struct ResourceRequest {
    id: ResourceId,
    page_id: PageId,
    url: String,
    kind: ResourceKind,
    headers: Vec<(String, String)>,
    timeout_ms: u64,
}

struct ResourceResponse {
    id: ResourceId,
    page_id: PageId,
    final_url: String,
    status: u16,
    content_type: Option<String>,
    body: Vec<u8>,
    protocol: NetworkProtocol,
}

The HTTP client fills in transport-level facts such as status, final URL, content type, body bytes, and negotiated protocol. The browser then decides how to interpret the bytes. A text/html main document goes to the HTML parser. A stylesheet goes to CSS parsing. An image response goes to image decoding. A script response goes to the JavaScript loading path.

HTTP Client Construction

The browser should construct the HTTP client once per loader or worker context, not rebuild it for every asset. That lets connection reuse and HTTP/2 negotiation work as intended.

struct BrowserHttpClient {
    client: reqwest::blocking::Client,
    config: HttpClientConfig,
}

struct HttpClientConfig {
    user_agent: String,
    accept_language: String,
    connect_timeout_ms: u64,
    request_timeout_ms: u64,
}

impl BrowserHttpClient {
    fn new(config: HttpClientConfig) -> Result<Self, LoadError> {
        let client = reqwest::blocking::Client::builder()
            .user_agent(config.user_agent.clone())
            .connect_timeout(std::time::Duration::from_millis(config.connect_timeout_ms))
            .timeout(std::time::Duration::from_millis(config.request_timeout_ms))
            .https_only(false)
            .build()
            .map_err(|err| LoadError::ClientBuild(err.to_string()))?;

        Ok(Self { client, config })
    }
}

The GUI should not own this client directly. It belongs to the loading service or page worker because that is where blocking work is allowed.

Browser Headers

Headers are part of browser identity and resource policy. They should be generated in one place so document, stylesheet, script, and image requests stay consistent.

fn default_headers(config: &HttpClientConfig, kind: ResourceKind) -> Vec<(String, String)> {
    let accept = match kind {
        ResourceKind::Document => "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
        ResourceKind::Stylesheet => "text/css,*/*;q=0.1",
        ResourceKind::Script => "*/*",
        ResourceKind::Image => "image/avif,image/webp,image/png,image/svg+xml,image/*,*/*;q=0.8",
    };

    vec![
        ("Accept".to_string(), accept.to_string()),
        ("Accept-Language".to_string(), config.accept_language.clone()),
        ("Connection".to_string(), "keep-alive".to_string()),
    ]
}

fn apply_headers(
    mut builder: reqwest::blocking::RequestBuilder,
    headers: &[(String, String)],
) -> reqwest::blocking::RequestBuilder {
    for (name, value) in headers {
        builder = builder.header(name.as_str(), value.as_str());
    }
    builder
}

Request headers should be visible in telemetry when debugging is enabled, but sensitive values should not be logged casually if the browser later supports cookies or authentication.

Dispatching A Request

The request dispatcher converts browser-owned ResourceRequest into a reqwest request, then converts the reqwest response back into browser-owned data.

impl BrowserHttpClient {
    fn fetch(&self, request: ResourceRequest) -> Result<ResourceResponse, LoadError> {
        let started = now_ms();
        let headers = merge_headers(
            default_headers(&self.config, request.kind),
            request.headers.clone(),
        );

        let builder = self.client.get(&request.url);
        let builder = apply_headers(builder, &headers);
        let response = builder
            .send()
            .map_err(|err| LoadError::Network(err.to_string()))?;

        let status = response.status().as_u16();
        let final_url = response.url().to_string();
        let protocol = classify_protocol(response.version());
        let content_type = response
            .headers()
            .get(reqwest::header::CONTENT_TYPE)
            .and_then(|value| value.to_str().ok())
            .map(str::to_string);

        let body = response
            .bytes()
            .map_err(|err| LoadError::BodyRead(err.to_string()))?
            .to_vec();

        Ok(ResourceResponse {
            id: request.id,
            page_id: request.page_id,
            final_url,
            status,
            content_type,
            body,
            protocol,
            elapsed_ms: now_ms().saturating_sub(started),
        })
    }
}

This shape keeps reqwest at the edge. The parser never sees reqwest::Response; it sees bytes plus metadata.

Protocol Classification

Protocol classification is useful for telemetry and performance analysis. It should be observational: the browser records what happened, then can later choose different scheduling policies.

fn classify_protocol(version: reqwest::Version) -> NetworkProtocol {
    match version {
        reqwest::Version::HTTP_09
        | reqwest::Version::HTTP_10
        | reqwest::Version::HTTP_11 => NetworkProtocol::Http1,
        reqwest::Version::HTTP_2 => NetworkProtocol::Http2,
        reqwest::Version::HTTP_3 => NetworkProtocol::Http3,
        _ => NetworkProtocol::Unknown,
    }
}

enum NetworkProtocol {
    File,
    Http1,
    Http2,
    Http3,
    Unknown,
}

If the browser later adds HTTP/3 or a custom HTTP/2 scheduler, this enum can grow without changing HTML, CSS, layout, or rendering code.

HTTP/2-Specific Shape

HTTP/2 is still accessed through reqwest, but the browser should treat it as a different scheduling situation. The important difference is that one connection can carry multiple streams for the same origin. The browser does not need to implement HTTP/2 frames directly, but it should record when HTTP/2 is used and avoid policies that assume every request is a separate HTTP/1-style connection.

#[derive(Clone, Debug, PartialEq, Eq, Hash)]
struct OriginKey {
    scheme: String,
    host: String,
    port: Option<u16>,
}

impl OriginKey {
    fn from_url(url: &str) -> Result<Self, LoadError> {
        let parsed = parse_url(url)?;
        Ok(Self {
            scheme: parsed.scheme,
            host: parsed.host,
            port: parsed.port,
        })
    }
}

The loader can keep lightweight per-origin protocol state. This is not a replacement for reqwest connection pooling; it is browser-side knowledge used for scheduling and telemetry.

struct OriginNetworkState {
    protocol: Option<NetworkProtocol>,
    in_flight: usize,
    completed: usize,
    failed: usize,
    last_request_started_ms: u64,
}

struct NetworkScheduler {
    origins: std::collections::HashMap<OriginKey, OriginNetworkState>,
}

When a response arrives, the browser updates the origin state with the negotiated protocol.

impl NetworkScheduler {
    fn observe_response(&mut self, url: &str, protocol: NetworkProtocol, ok: bool) {
        if let Ok(origin) = OriginKey::from_url(url) {
            let state = self.origins.entry(origin).or_insert(OriginNetworkState {
                protocol: None,
                in_flight: 0,
                completed: 0,
                failed: 0,
                last_request_started_ms: 0,
            });

            state.protocol = Some(protocol);
            state.in_flight = state.in_flight.saturating_sub(1);
            if ok {
                state.completed += 1;
            } else {
                state.failed += 1;
            }
        }
    }
}

HTTP/2 should allow more overlap than conservative HTTP/1 pacing, but the browser can still keep a polite cap to avoid flooding servers or starving page work.

fn max_in_flight_for(protocol: Option<NetworkProtocol>, kind: ResourceKind) -> usize {
    match (protocol, kind) {
        (Some(NetworkProtocol::Http2), ResourceKind::Image) => 6,
        (Some(NetworkProtocol::Http2), _) => 4,
        (_, ResourceKind::Image) => 1,
        _ => 2,
    }
}

fn can_start_request(state: &OriginNetworkState, kind: ResourceKind) -> bool {
    state.in_flight < max_in_flight_for(state.protocol, kind)
}

The browser should also record HTTP/2 stream-style behavior in telemetry, even though stream ids are not exposed by the high-level HTTP client.

enum NetworkTelemetry {
    RequestQueued {
        resource_id: ResourceId,
        origin: OriginKey,
        kind: ResourceKind,
    },
    RequestStarted {
        resource_id: ResourceId,
        origin: OriginKey,
        in_flight_for_origin: usize,
    },
    ProtocolObserved {
        resource_id: ResourceId,
        origin: OriginKey,
        protocol: NetworkProtocol,
    },
    ResponseCompleted {
        resource_id: ResourceId,
        status: u16,
        elapsed_ms: u64,
        protocol: NetworkProtocol,
    },
}

Fallback should be boring. If HTTP/2 negotiation does not happen, reqwest returns an HTTP/1.x response version and the browser schedules future requests with HTTP/1 assumptions. The page pipeline should not care which protocol delivered the bytes.

fn scheduling_policy_after_response(
    scheduler: &mut NetworkScheduler,
    response: &ResourceResponse,
) {
    scheduler.observe_response(
        &response.final_url,
        response.protocol,
        (200..400).contains(&response.status),
    );
}

Redirects And Final URLs

The final URL matters because relative links and subresources should resolve against the document that actually loaded, not necessarily the URL the user typed.

struct LoadedDocument {
    requested_url: String,
    final_url: String,
    html: String,
    content_type: Option<String>,
}

fn base_url_for_document(document: &LoadedDocument) -> &str {
    &document.final_url
}

The loader should also record redirects in telemetry when possible:

enum LoadTelemetry {
    RequestStarted { id: ResourceId, url: String, kind: ResourceKind },
    ResponseReceived { id: ResourceId, status: u16, protocol: NetworkProtocol },
    RedirectObserved { id: ResourceId, from: String, to: String },
    RequestFailed { id: ResourceId, reason: String },
}

Connecting Responses To The Pipeline

After a response is loaded, the browser dispatches it by resource kind.

fn consume_resource(page: &mut PageState, response: ResourceResponse) -> Result<(), PageFailure> {
    match response.kind {
        ResourceKind::Document => {
            let html = decode_text(&response)?;
            page.document = Some(parse_html(&html)?);
            page.base_url = response.final_url;
        }
        ResourceKind::Stylesheet => {
            let css = decode_text(&response)?;
            page.stylesheets.push(parse_css(&css)?);
        }
        ResourceKind::Script => {
            let source = decode_text(&response)?;
            page.pending_scripts.push(source);
        }
        ResourceKind::Image => {
            page.image_results.push(decode_image(response.body)?);
        }
    }
    Ok(())
}

This is the key architecture rule: HTTP is transport. The browser pipeline interprets the response.

Main Document Loading

The main document is the first resource fetched for a navigation. If the user enters an address, clicks a link, submits a form, or selects a history entry, the browser starts by loading the main document for that navigation.

The GUI should not block while this happens. Page loading can be slow, a server can stall, and a script can later fail. The window shell should remain able to update tabs, loading labels, progress bars, menus, and navigation buttons while the page worker performs network and parsing work.

The output of main document loading is usually:

  • the final URL after redirects,
  • the response status and headers,
  • the HTML text or error body,
  • a base URL for resolving relative resources,
  • telemetry describing what happened.

Subresources

Subresources are files referenced by the main document. Common examples are:

  • CSS files from <link rel="stylesheet" href="...">,
  • JavaScript files from <script src="...">,
  • images from <img src="...">,
  • icons and metadata from <link> elements.

Stylesheets and scripts can affect page structure or appearance, so they are often part of the initial page analysis. Images can be loaded late: the page can first paint gray placeholders, then replace those placeholders when image bytes arrive and decode successfully.

This split matters for responsiveness. A browser should not wait forever for every image before showing text. At the same time, it should continue loading images after the page first appears, and it should update the visible page when late image loading completes.

Loading Policy

The loading policy is the set of practical rules used when the ideal browser behavior would be too expensive or not implemented yet.

AlmostThere uses conservative resource pacing for image requests so it does not send too many nearly simultaneous requests to the same server. It records image attempts, failures, retry pauses, and completion in telemetry. When a page or tab closes, the pending image queue should be cleared so stale requests do not update the wrong page later.

For scripts and other blocking resources, the browser uses budgets and timeout-like policies to avoid letting one broken resource freeze the whole page forever. When a resource times out or fails, the browser should prefer a clear error event in telemetry over a silent hang.

Debugging This Layer

When a page looks wrong, first ask whether the bytes arrived.

Useful questions:

  • Did the main document load successfully?
  • Was there a redirect?
  • Was the final URL the expected one?
  • Did the stylesheet load, or is the page using fallback/default styles?
  • Did the script load but fail during execution?
  • Are images missing because the URLs were wrong, the requests failed, or decoding failed?
  • Did late image loading update the page after first paint?

If the answer is not visible from the screen, inspect JSONL telemetry before changing layout or rendering code. A missing stylesheet can look like a CSS bug, and a failed script can look like an HTML parsing bug.
