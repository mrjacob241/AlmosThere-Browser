Page-Agnostic Fix Strategy

A page-agnostic fix improves a general browser rule. It does not recognize a site, URL, title, or one-off markup pattern and move pixels until the screenshot looks better.

This strategy is central to AlmostThere Browser. The project uses real pages as diagnostics, but the final fix should usually live in HTML parsing, CSS computation, layout, rendering, networking, JavaScript, or input handling.

How This Relates To AlmostThere Browser

AlmostThere is still incomplete, so it is tempting to patch individual pages. That produces short-term wins and long-term fragility. A standards-oriented, page-agnostic fix makes the next page more likely to work too.

For example, if Ecosia buttons shift right because flex auto sizing ignores children, the fix belongs in flex sizing. If Wikipedia links have spacing gaps because anchors are laid out as isolated boxes, the fix belongs in inline rich text flow and link hit boxes.

From Symptom To Rule

The workflow is:

  • Capture the live-page symptom.
  • Inspect telemetry and render/layout dumps.
  • Identify the first wrong layer.
  • Build a focused fixture for the general pattern.
  • Compare with a reference browser.
  • Implement the general rule.
  • Recheck the fixture and live page.

This prevents a fix from merely matching one screenshot.

Good Fixes

Good fixes include:

  • child-aware auto sizing,
  • normal inline flow for anchor text,
  • correct whitespace preservation around tags,
  • image placeholders updated by late loads,
  • host APIs that mutate style generally,
  • script budgets with clear errors,
  • URL resolution based on base URL rules.

Bad Fixes

Bad fixes include:

  • if url contains wikipedia,
  • adding arbitrary offsets for one page,
  • forcing one known title to a custom width,
  • skipping a script only by filename,
  • hiding one bad element class without understanding display rules.

Diagnostics can mention real pages. Production rules should not depend on them unless the feature is explicitly site-specific, such as a bookmark entry.

Debugging This Strategy

If a fix improves one page and breaks another, it may have encoded the wrong abstraction. Reproduce both cases as fixtures, then identify the standard rule that covers both.

When uncertain, prefer a narrower general rule over a broad arbitrary heuristic.

Rust Shape

General fixes often become reusable rules or helpers instead of URL checks.

fn resolve_auto_width(style: &ComputedStyle, parent: Size, children: &[PreferredSize]) -> f32 {
    match style.width {
        Length::Px(px) => px,
        Length::Percent(percent) => parent.width * percent,
        Length::Auto => {
            let children_width = children.iter().map(|child| child.min_width).fold(0.0, f32::max);
            children_width.max(parent.width)
        }
    }
}

fn is_bad_fix(url: &str) -> bool {
    url.contains("one-specific-site.example")
}

The first function encodes a reusable sizing rule. The second function is the kind of site-specific test this project normally avoids.
