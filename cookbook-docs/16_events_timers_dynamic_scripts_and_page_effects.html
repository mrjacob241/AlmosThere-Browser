Events, Timers, Dynamic Scripts, And Page Effects

Dynamic pages change after the initial HTML is parsed. Events, timers, and scripts are the mechanisms that make those changes happen.

This section focuses on the flow from a browser event to JavaScript execution and then back into page state.

How This Relates To AlmostThere Browser

AlmostThere receives input and loading events from the shell and page worker. Some events have default browser behavior, and some are delivered to JavaScript. JavaScript may then emit effects such as style changes, text updates, or new resource requests.

The browser should keep this loop explicit:

browser event -> script callback -> browser effect -> style/layout/render update

Events

Common events include:

  • click,
  • input,
  • keydown,
  • submit,
  • load,
  • error,
  • timeout callbacks.

Each event needs a type, a target, and enough metadata for common handlers. The target should usually be the relevant element, not just the global window.

Timers

Timers schedule work for later. setTimeout runs once after a delay. setInterval repeats. A basic implementation can begin with bounded queues and predictable execution order.

Timer callbacks should be budgeted. A timer should not become a hidden infinite loop that freezes the browser.

Dynamic Scripts

Pages can create script elements or request additional scripts after the initial document load. A browser-like implementation treats this as another resource load plus an execution step.

Dynamic script support should preserve ordering where required and report failures clearly. Unsupported dynamic behavior should produce telemetry rather than silent missing content.

Page Effects

Script effects should be applied through the page model:

  • change style,
  • change classes,
  • change attributes,
  • insert or remove nodes,
  • update text,
  • trigger navigation,
  • schedule resource loading.

After effects are applied, the browser may need to recompute style, rerun layout, rebuild render graph objects, and repaint.

Debugging This Layer

If a click does nothing, check whether the event target was found, whether a listener existed, whether the callback ran, and whether it emitted effects. If content appears too late or never appears, inspect timer queues and dynamic script loads.

Rust Shape

Events and timers are queues of scheduled script work plus resulting page effects.

struct Event {
    kind: String,
    target: NodeId,
}

struct TimerTask {
    due_ms: u64,
    callback: ObjectId,
}

fn dispatch_event(runtime: &mut JsRuntime, event: Event) -> Result<Vec<BrowserEffect>, JsError> {
    runtime.call_event_listeners(event)
}

fn run_due_timers(runtime: &mut JsRuntime, now_ms: u64) -> Vec<BrowserEffect> {
    runtime.take_due_timers(now_ms)
        .into_iter()
        .flat_map(|task| runtime.call_timer(task).unwrap_or_default())
        .collect()
}

The browser can then apply effects and trigger style/layout/render invalidation.
