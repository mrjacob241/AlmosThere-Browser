Failure Modes, Crash Isolation, And Recovery

Browsers run untrusted, complex, and frequently broken content. A page can recurse forever, load too slowly, crash a script, request missing assets, or produce malformed markup.

The browser should treat failure as a normal state, not as an exceptional surprise.

How This Relates To AlmostThere Browser

AlmostThere separates the GUI from page work so the user can still interact with the shell when a page fails. A page may show an error, but tabs, menus, history, and diagnostics should remain reachable.

This is a quality-of-life feature and a debugging feature. If the shell survives, telemetry can be saved and the user can continue testing.

Common Failures

Common failure modes include:

  • network timeout,
  • redirect loop,
  • stylesheet failure,
  • image decode failure,
  • script exception,
  • script budget exhaustion,
  • recursion or stack overflow,
  • malformed HTML,
  • layout collapse,
  • render graph inconsistency,
  • stale worker update after navigation.

Each failure should have a clear diagnostic event where practical.

Recovery Behavior

Recovery can take several forms:

  • continue with missing resource,
  • show a placeholder,
  • disable a failing script,
  • stop loading one page,
  • show a tab-level error,
  • ignore late updates from old page id,
  • allow reload to try again.

The user-facing message can be simple, but telemetry should be specific.

Isolation Principles

One broken page should not crash the entire application. One broken script should not freeze every tab. One failed image should not prevent text from rendering.

Isolation is not only process-level. Budgets, queues, page ids, tab ids, and cancellation checks also protect the rest of the browser.

Debugging This Layer

When investigating a crash or hang, identify the last successful boundary:

  • UI event,
  • navigation start,
  • response received,
  • parser started,
  • CSS computed,
  • script entered,
  • layout started,
  • render graph emitted,
  • paint requested.

The fix belongs at the first boundary where the system stopped behaving defensively.

Rust Shape

Failure handling should distinguish page-level failure from shell-level failure.

enum PageFailure {
    NetworkTimeout,
    ScriptBudgetExceeded { script_url: Option<String> },
    WorkerCrashed { detail: String },
    LayoutFailed { detail: String },
}

enum RecoveryAction {
    ContinueWithPlaceholder,
    ShowTabError(String),
    StopPageWorker(PageId),
    IgnoreStaleMessage(PageId),
}

fn recover_from_failure(failure: PageFailure) -> RecoveryAction {
    match failure {
        PageFailure::NetworkTimeout => RecoveryAction::ShowTabError("Page load timed out".into()),
        PageFailure::ScriptBudgetExceeded { .. } => RecoveryAction::ContinueWithPlaceholder,
        PageFailure::WorkerCrashed { detail } => RecoveryAction::ShowTabError(detail),
        PageFailure::LayoutFailed { detail } => RecoveryAction::ShowTabError(detail),
    }
}

The GUI can stay alive even when the page switches to an error state.
