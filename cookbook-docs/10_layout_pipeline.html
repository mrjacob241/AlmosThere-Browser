Layout Pipeline

Layout turns styled document nodes into boxes with positions and sizes. It is the stage where abstract content becomes spatial: paragraphs get line boxes, flex containers place children, images reserve area, and the page receives a scrollable height.

Most visual browser bugs pass through layout. If a column is too narrow, a block starts too far right, a line collapses to zero height, or table-like content overlaps, the layout pipeline is usually involved.

How This Relates To AlmostThere Browser

AlmostThere receives parsed HTML and computed CSS, then builds a layout representation that later becomes render graph objects. Layout is responsible for preserving browser-like relationships between parent boxes, child boxes, inline text, replaced elements, and available viewport width.

The layout layer should not guess page intent from URLs. It should apply general rules: block formatting, inline text flow, flex sizing, grid-like child awareness, margin and padding constraints, min/max sizing, and intrinsic sizes.

Inputs And Outputs

Inputs:

  • document tree,
  • computed style,
  • viewport size,
  • image intrinsic sizes when available,
  • text measurement from the canvas/font layer,
  • form and replaced-element metadata.

Outputs:

  • positioned boxes,
  • line boxes and text fragments,
  • scrollable document size,
  • intrinsic or preferred sizes,
  • renderable rectangles and content boundaries,
  • hit-test source regions.

Block And Inline Flow

Block layout stacks boxes vertically. Each block usually uses the available width of its containing block unless CSS says otherwise.

Inline layout places text and inline elements into line boxes. A link inside a sentence should share line flow with surrounding text. It should not be laid out as a disconnected block unless CSS makes it block-level.

The line layout must decide where words fit, when to wrap, and how tall each line is. It should preserve normal spaces while avoiding fake newlines in copied text caused only by visual wrapping.

Flex And Grid-Like Layout

Flex and grid are child-aware systems. A parent cannot choose correct dimensions without considering what its children need. Auto sizing must account for content, preferred size, min-content size, max constraints, and available space.

A recurring failure mode is treating auto as zero or as a fixed arbitrary value. That can collapse columns, push content to the right, or make text render as a vertical stack of words. A better implementation computes preferred child sizes first, then resolves the parent.

Intrinsic And Preferred Sizes

Intrinsic size comes from content. Text has a preferred width based on words and measurement. Images have natural dimensions after decoding. Inputs and buttons have default usable sizes. Replaced elements often need aspect-ratio behavior.

Preferred size is not always final size. A box may prefer to be wide but shrink due to available space. It may also have a minimum size that prevents complete collapse.

Debugging This Layer

When diagnosing layout:

  • inspect computed display and width values first,
  • compare parent and child boxes,
  • check whether auto sizes used child measurements,
  • verify line boxes against text fragments,
  • inspect margins, padding, and gap handling,
  • reduce the issue into a color layout fixture.

If a fixture passes but a live page fails, the fixture is probably missing a critical parent style, percentage, nested flex rule, or intrinsic-size dependency.

Rust Shape

Layout code should turn styled nodes into explicit geometry. Auto sizing should be resolved with child measurements, not guessed as zero.

struct LayoutInput<'a> {
    document: &'a Document,
    styles: &'a StyleMap,
    viewport_width: f32,
}

#[derive(Debug, Clone)]
struct LayoutBox {
    node_id: NodeId,
    rect: Rect,
    children: Vec<LayoutBox>,
}

fn layout_node(input: &LayoutInput<'_>, node_id: NodeId, available: Size) -> LayoutBox {
    let preferred = measure_children(input, node_id, available);
    let rect = resolve_box_rect(input.styles, node_id, available, preferred);
    LayoutBox { node_id, rect, children: Vec::new() }
}

The important pattern is measuring children before finalizing parent dimensions when CSS requires child-aware behavior.
