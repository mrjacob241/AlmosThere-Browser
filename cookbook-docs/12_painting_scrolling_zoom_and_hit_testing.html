Painting, Scrolling, Zoom, And Hit Testing

Painting turns render objects into pixels. Scrolling changes which part of the document is visible. Zoom changes the scale of the page. Hit testing maps pointer coordinates back to page objects.

These operations must agree on the same coordinate system. If zoom or scroll is applied in painting but not hit testing, links and selections drift away from visible text.

How This Relates To AlmostThere Browser

AlmostThere uses the canvas layer as the final page surface. The browser gives it renderable content and viewport state; the canvas paints what is visible and reports interaction events back to the shell or page model.

Zoom and scroll are browser-level presentation state. They should not rewrite the underlying HTML or CSS. They should transform the page view while preserving content geometry.

Painting Order

Painting order determines what appears above what. A simplified order is:

  • backgrounds,
  • borders and separators,
  • images and placeholders,
  • text,
  • controls,
  • selection highlights and carets,
  • debug overlays.

Real CSS has more complex stacking rules, but a stable simplified order is better than arbitrary drawing. It prevents text from being hidden behind backgrounds and makes overlays predictable.

Scrolling

The document may be taller or wider than the viewport. Scrolling changes the viewport origin. The page content keeps its document coordinates; painting subtracts the scroll offset to determine screen position.

Smooth scrolling is a presentation effect. It should end at the intended final offset and stop cleanly when input ends or when content bounds are reached.

Zoom

Zoom scales the page. Browser-like zoom should keep the user's focus area stable where possible. If the user zooms with the mouse over a paragraph, the scroll offset should adjust so that paragraph remains near the pointer.

Zoom also changes scroll extents. A zoomed page may need horizontal scrolling even if the unzoomed page fit inside the viewport.

Hit Testing

Hit testing starts with a screen coordinate and asks what page object is under it. The coordinate must be converted through zoom and scroll into document coordinates.

Common hit-test targets include:

  • links,
  • form controls,
  • selectable text,
  • scrollbars,
  • context menu targets,
  • debug regions.

Hit testing should prefer interactive objects where the user expects them. Text selection and link clicks can overlap, so the browser needs clear rules for drag versus click.

Debugging This Layer

When clicks land in the wrong place, log the screen coordinate, scroll offset, zoom factor, transformed document coordinate, and selected hit object. When zoom feels wrong, inspect whether the scroll offset compensates around the pointer. When text is clipped, inspect both object rectangles and clipping rectangles.

Rust Shape

Painting and hit testing should use one coordinate transform so visible pixels and interaction regions agree.

struct ViewTransform {
    scroll_x: f32,
    scroll_y: f32,
    zoom: f32,
}

impl ViewTransform {
    fn screen_to_document(&self, point: Point) -> Point {
        Point {
            x: point.x / self.zoom + self.scroll_x,
            y: point.y / self.zoom + self.scroll_y,
        }
    }

    fn document_to_screen(&self, point: Point) -> Point {
        Point {
            x: (point.x - self.scroll_x) * self.zoom,
            y: (point.y - self.scroll_y) * self.zoom,
        }
    }
}

If rendering and hit testing use different transforms, links, selection, and hover states will drift.
